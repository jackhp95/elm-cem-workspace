# Spec F — Delete `raw-html` by generating structural Elm previews

Date: 2026-08-05
Repo: `elm-m3e`
Status: approved design, not yet planned
Supersedes: the "narrow, don't delete" position in
`specs/2026-08-05-icon-registry-seam-design.md`

## Problem

`js/raw-html.js` parses an HTML string into a `<template>` and adopts the nodes into the live
DOM. That is a DOM-XSS sink, guarded only by a comment asking callers to behave. Spec C
removed one of its two callers (the GitHub mark). This spec removes the other and deletes the
element.

The earlier position was that the remaining caller, `Doc.rawPreview`, was legitimate because
the preview needs live DOM so the embedded `<m3e-*>` elements upgrade in place. **That
reasoning was wrong.** Custom elements upgrade whenever *any* DOM API creates them, including
Elm's virtual DOM — which is precisely what the entire typed M3e library relies on for every
other component on the site. `innerHTML` was never required for upgrade. It was required only
because the markup arrives as an opaque `String`.

## What `rawPreview` actually does

The full chain:

```
config/examples.rich.json              mined from matraic's upstream docs
  └─ docs/scripts/examples-gen/examples-to-elm.mjs    linkedom parse → TYPED-Elm conversion
       └─ config/examples.generated.json              { title, code, section }
            └─ docs/scripts/build-examples-data.mjs
                 └─ docs/data/examples.json           ← elm-pages BackendTask
                      └─ UsageExample { title, html, … }
```

```elm
-- docs/src/Doc/Usage.elm:170
, Doc.showcase (Doc.rawPreview ex.html)
```

```elm
-- docs/src/Doc.elm:65
rawPreview html =
    M3e.Unsafe.customElement "raw-html"
        [ M3e.Unsafe.Attributes.customAttribute "content" html, TA.class "max-w-full py-2" ] []
```

```js
// js/raw-html.js:33
const tpl = document.createElement("template");
tpl.innerHTML = next;
this.replaceChildren(tpl.content.cloneNode(true));
```

Its purpose is a live, themed rendering of each component example. It renders the HTML
*string* rather than the Elm because, per `examples-to-elm.mjs`'s own header, the typed
conversion **degrades**:

> A top that fails to compile (or that the converter couldn't map) is NULLED and the example
> is KEPT — it ships its always-present HTML surface.

HTML is the always-present surface; typed Elm is derived and may be absent. So the preview
uses the one that always exists.

## The insight that makes deletion work

The degradation is a property of mapping to the **typed** API — matching `variant="filled"` to
`M3e.Attributes.variant Value.filled`, satisfying kind rows, finding a setter for every
attribute. A **structural** conversion has none of those obligations and therefore cannot
fail: every element becomes `Html.node "<tag>"`, every attribute becomes `attribute "k" "v"`,
every text node becomes `Html.text`.

So the reason the HTML string is kept does not apply to a structural conversion. The preview
can be generated Elm while the *code display* keeps showing the original HTML source string,
which is what that pane is for.

## Design

### Generate structural preview modules

A new build step walks the same mined HTML with `linkedom` — already a dependency, already
used for this exact parsing in `examples-to-elm.mjs` and `docs/scripts/roundtrip/dom-diff.mjs`
— and emits one Elm module per component:

```elm
-- GENERATED by docs/scripts/previews-gen/previews-to-elm.mjs — do not edit.
module Gen.Preview.AppBar exposing (previews)

import Html exposing (Html)
import Html.Attributes exposing (attribute)


{-| Structural renderings of this component's mined examples, in corpus order.
-}
previews : List (Html msg)
previews =
    [ Html.node "m3e-app-bar"
        [ attribute "size" "medium" ]
        [ Html.node "m3e-icon-button"
            [ attribute "slot" "leading", attribute "aria-label" "Back" ]
            [ Html.node "m3e-icon" [ attribute "name" "arrow_back" ] [] ]
        , Html.node "span" [ attribute "slot" "title" ] [ Html.text "Top 10 hiking trails" ]
        ]
    ]
```

Every `<m3e-*>` there upgrades exactly as it does today. No `innerHTML`, no sanitizer, no
runtime parsing, no new Elm dependency, and no browser-support question.

### Conversion rules

The generator is deliberately dumb, because dumb cannot degrade:

- Element → `Html.node "<tag>" [attrs] [children]`. Always `Html.node`, never a typed helper
  — mapping to typed helpers is what introduces failure modes.
- Attribute → `attribute "<name>" "<value>"`. Boolean attributes present with an empty value
  (`filled=""`) keep the empty string, which is how the corpus already writes them and what
  the round-trip harness canonicalises against.
- Text node → `Html.text "<escaped>"`. Collapse insignificant whitespace using the same rule
  as `dom-diff.mjs` so previews and round-trip comparisons agree.
- Comment nodes → dropped.
- `<script>`, `<style>`, `<link>`, event-handler attributes (`on*`) → **fail the build
  loudly**, naming the component and example. The corpus is registration-only-card-filtered
  upstream so none should appear; if one does, that is a corpus change worth a human look, not
  something to silently strip. This is the enforcement the `raw-html` comment only requested.

### Call-site change

`Doc.rawPreview : String -> Element …` is deleted. `Doc.showcase` takes the generated `Html`
instead, wrapped back into the `Element` world at one structural seam:

```elm
-- docs/src/Doc/Usage.elm
, Doc.showcase (Doc.preview (previewFor ex))
```

`Doc.preview` wraps with the existing `max-w-full py-2` class and the block-flow comment that
`rawPreview` carried. The examples data keeps `ex.html` — the **code pane still displays the
HTML source**, which is a string in a `<pre>`, not a DOM sink.

Previews are looked up by corpus index, the same key `Doc/Usage.elm` already uses for
`model.surfaces`. The generator must emit previews in corpus order and the lookup must be
total: an out-of-range index returns an empty preview rather than crashing, and the generator
asserts count parity with `docs/data/examples.json` so a mismatch fails the build.

### Then delete the element

- Delete `js/raw-html.js`.
- Remove its import from `docs/index.ts`.
- Remove the `raw-html` prose from `docs/composition.md` and any `style.css` rule targeting it.
- Update `docs/tests-browser/usage.spec.ts` if it asserts on `raw-html`.

After this there is **no `innerHTML` sink in the docs app at all** — not a sanitized one, not
a trusted one. That is a stronger claim than any allowlist, and it is greppable:
`rg -n 'innerHTML|setHTMLUnsafe|insertAdjacentHTML' js docs/scripts docs/*.ts`.

## Why not `setHTML` / the Sanitizer API

The modern-web guidance does endorse `setHTML` over `innerHTML` in general
("DO: Use `setHTML` (part of the Sanitizer API) when available to safely insert HTML"), so
it deserves an explicit rejection rather than silence:

1. It narrows what survives a string→DOM path; it does not remove the path.
2. Its allowlist is built for known HTML. Custom elements are not in it, so every `<m3e-*>`
   tag and attribute would need explicit allowlisting — generating a config from the CEM
   purely to re-permit exactly what is being injected. Considerable machinery to make
   injection safe when the injection is avoidable.
3. It is not Baseline widely available, so it needs a fallback, and the only fallback is
   `innerHTML` — i.e. the sink stays. (Verify current support before relying on this reasoning
   if the decision is ever revisited.)

Build-time conversion has none of these properties because there is no runtime string.

## Cost, stated honestly

`ex.html` is currently *runtime data*; previews become *generated code*. That means a new
generated Elm surface (`docs/gen/Preview/*.elm` or one module with a dispatch), a new entry in
the `gen` chain, a drift check, and `elm.json` source-directory wiring. It is more machinery
than a comment rewrite. The payoff is deleting a DOM-XSS sink outright and making the
"previews contain only what the corpus declared" property enforced by a build failure rather
than asserted by a comment.

## Verification

- Every component's Usage page renders live, themed previews identical to before —
  spot-check several against `git stash`-ed output, and rely on the existing
  `docs/scripts/roundtrip/` DOM diff, which already compares mined HTML against rendered
  output and is the natural gate for "the structural conversion is faithful".
- `rg -n 'raw-html' --glob '!node_modules' .` returns nothing.
- `rg -n 'innerHTML' js docs/scripts docs/*.ts` returns nothing.
- `M3e.Unsafe.fromHtml` / `M3e.Unsafe.customElement` use in `docs/src/Doc.elm` drops by one.
- Generator tests for each loud-failure path: `<script>`, an `on*` attribute, and a
  count mismatch against `examples.json`.
- Drift check green; `npm run test:browser` green.
