# Diagnosis — Compose §1.3 "pressed ≠ applied" (the chip lies about state)

**Date:** 2026-08-15
**Method:** systematic-debugging (root-cause before fix). Traced the data flow through
the Elm route, the headless core, the codegen fold, and the m3e-button web component;
reproduced against the real browser via the existing Playwright suite.
**Driver:** [`2026-08-15-compose-ia-review.md`](2026-08-15-compose-ia-review.md) §1.3 / §3.3 / §4 (priority 1).
**Verdict:** **DISPLAY-ONLY.** The chip's pressed/filled visual is genuinely
untrustworthy, but the model, live preview, and generated code **do** update correctly
when a menu value is actually selected. §1.3 is not a model-update bug.

---

## 1. What the audit reported

Selecting a value from an attribute menu (`variant → segmented`), adding a text child via a
slot menu (`leading → Text`), and loading an example via a slot menu (`overline → Typescale…`)
all marked the corresponding chip **filled/[pressed]**, but "the live preview and the generated
Elm snippet never changed." The conclusion drawn was that "selecting a menu value doesn't
reliably update the model — the chip lies about state," escalated as a possible correctness bug
that should block sign-off (§3.3).

## 3. Root cause — the pressed state is bound to the web component, not the Elm model

The chip and the value-application are two independent clicks on two different elements. The
audit's "pressed" came from the **first** click (opening the menu); the value only applies on the
**second** click (the menu item). The two are decoupled by design of the m3e-button:

### 3.1 The mechanism (data flow, source-cited)

1. Every attribute chip (`Route/Components/Compose.elm` → `discreteAttrButtonElement:702`,
   `attrButtonElement:641` PlainChip branch) and every multi-option slot chip
   (`slotButtonElement:878`) is an `M3e.button` carrying **`M3e.Attributes.toggle True`** +
   **`M3e.Attributes.selected info.isSet`**. Its only wired message is
   `OpenMenu path (AttrMenu/SlotMenu name)`, plus a `menuTrigger [ for = <menuId> ]` child that
   opens the popover. The chip does **not** set the value; the menu items inside the popover do.
2. The m3e-button, when `toggle` is set, flips its **own** `selected` on every click —
   `packages/m3e-okf/.cache/m3e/packages/web/src/button/ButtonElement.ts:639`:
   ```ts
   if (this.toggle && !e.defaultPrevented) {
     if (this.dispatchEvent(new Event("beforeinput", { cancelable: true }))) {
       this.selected = !this.selected;   // <-- self-managed, client-side, no Elm msg
   ```
   `selected` is `@property({ type: Boolean, reflect: true })` (`:551`) and drives `ariaPressed`
   (`:623`) and the `--m3e-button-selected-*` container/label styling. So the open-click alone
   turns the chip "pressed/filled" — before any value is chosen.
3. The Elm model is unchanged by that open-click (only `OpenMenu` fired, which sets `openMenu`,
   not any attr/child). `info.isSet` is still `False`. On the next Elm render the vdom's
   `selected` value is still `False` — **identical to the previous render** — so Elm's
   virtual-DOM diff produces **no patch** for the `selected` attribute and never overwrites the
   `selected=true` the web component set on itself. The DOM keeps the stale pressed state.
4. When the user then clicks a menu item, `SetAttr`/`AddTextChild`/`AddChild` fires and the model
   *does* update — but the chip was already pressed from step 2, so the visual carries no
   information about whether step 4 happened. Equally, if the user opens a menu and dismisses it
   **without** selecting, the chip stays pressed with nothing applied.

### 3.2 Why Elm can't "just re-assert it"

This is the classic Elm + stateful-custom-element pitfall: a web component that mutates a
reflected property from its own event handler will not be corrected by Elm's vdom, because Elm
only patches attributes whose *virtual* value changed between renders. `selected` went
`False → False` in Elm's view of the world, so there is nothing to patch. The web component and
the model diverge and stay diverged.

### 3.3 The core is not implicated

`Cem/Compose.elm`'s `update`/`SetAttr`/`addIfAfforded` and `Compose/Codegen.elm`'s pure fold are
correct; `attrChips`/`slotChips` compute `isSet`/`filled` correctly from the model. Nothing in the
published headless core needs to change. The defect is entirely in the **consumer route's choice
of `toggle True` on a menu-opening button.**

## 4. Proposed fix (NOT applied — awaiting human sign-off)

Confined to the **docs-app consumer route** `packages/elm-m3e/docs/app/Route/Components/Compose.elm`
— it does **not** touch the published core `packages/elm-cem-compose/src/Cem/Compose.elm`, so it is
the lower-stakes class of change. Still reported first per the brief.

**Fix:** stop using the web component's self-managing `toggle` to represent applied-state. Drop
`M3e.Attributes.toggle True` from the three chip builders (`discreteAttrButtonElement`, the
PlainChip branch of `attrButtonElement`, and `slotButtonElement`) and keep only
`M3e.Attributes.selected info.isSet` / `selected (info.filled > 0)`. `selected` still reflects and
still drives the `[selected]` container/label styling, but it is now **purely model-derived**: the
chip is pressed iff the model says the attribute is set / the slot has content, and the
open-click no longer self-flips it. This makes the pressed signal trustworthy and, as a bonus,
removes the misleading `aria-pressed` toggle semantics from a control that is really a
menu-opener (`aria-haspopup` via the trigger is the honest semantics).

**Verification for the fix (when authorized):**
- Extend `compose.spec.ts` with a regression test that **opens a chip's menu and dismisses it
  without selecting**, then asserts the chip is **not** in the pressed/selected state and the
  snippet is unchanged — the assertion that would have caught this.
- Assert the positive path still presses correctly *after* a value is applied (guard against
  over-correcting to "never pressed").
- `build:site` + `check:review` + the full `compose.spec.ts` green.

**Caveats to check during implementation (not blockers, but verify):**
- Confirm `menuTrigger` still opens the popover when hosted in a non-`toggle` `M3e.button`
  (the trigger is a separate child element addressed by `for`, so this should be unaffected —
  the existing tests already click these menus open, and they must stay green).
- The `selected`-styling still needs `info.isSet` to be visually distinct from unset; verify the
  elevated-vs-filled variant swap the code already does (`variant = if isSet then filled else
  elevated`) reads correctly once `toggle` is gone.

This fix overlaps with the IA rework's §3.2/§3.3 ("reserve the filled chip style exclusively for
'this has content'"); see the IA-rework plan — it is scoped there as the first, correctness-gating
part so the two don't collide.

## 5. Bottom line

- **Not a model bug; do not block on a core-API change.** The published `Cem.Compose` core and the
  codegen are correct.
- **The audit's underlying complaint is real and worth fixing:** the pressed visual is decoupled
  from the model (bound to the m3e-button's own `toggle` state), so it is not trustworthy feedback
  — precisely the "visual layer can silently drift from the actual output" concern, just located
  in the chip's `toggle` attribute rather than in the edit pipeline.
- **The fix is a consumer-route change** (remove `toggle True` from three chip builders), low-risk,
  regression-testable, and is folded into the IA-rework plan as its correctness-gating first part.
