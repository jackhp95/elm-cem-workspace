## 1. What Compose is

Compose is an interactive editor for building a **valid tree of custom elements** by clicking,
where the set of things you are allowed to click at any moment is derived from a machine-readable
manifest of the component library rather than hand-written per component.

Each element in the tree is drawn as a card. The card's header names the component. A chip-set on
the card shows:

- **one chip per configurable attribute** the component exposes — plain when unset, filled when set;
- **one chip per slot** the component declares — showing how many children it currently holds.

Clicking an attribute chip opens a menu of that attribute's legal values. Clicking a slot chip
opens a menu of **everything that slot legally accepts** — plain text, an icon, and each component
its `kinds` name — and the user picks which of those the new child is. Choosing an option applies it
immediately, and two adjacent panes update:

1. a **live preview** — the real `m3e-*` (or `<brand>-*`) elements, actually rendered in the DOM;
2. a **copyable Elm snippet** that reproduces exactly that tree through the library's typed API.

The tagline from the brainstorming session: *incremental disclosure of the type system using
tangible outputs.* You do not need to read the docs for `m3e-list-item` to discover that it has a
`leading` slot that accepts an icon; you click the slot chip and the menu tells you.

### 1.1 Why it must be generic

The hard requirement is that Compose is **a capability of the `elm-cem` facts system, not a
feature of `elm-m3e`.** Any library generated by `elm-cem` must be able to stand up its own
Compose UI by writing a thin adapter, not by forking the engine.

This is achievable because of a contract `elm-cem` already enforces mechanically. Every generated
library exposes a module `<Brand>.Review.Facts` whose sole public value is

```elm
facts : List Fact
```

typed by `Cem.Facts.Fact`, and which imports nothing but `Cem.Facts`
(`packages/elm-cem/bin/elm-cem.js:702-713`, `packages/elm-cem/bin/family-deps.js:12-15`, and the
`syncExposedModules` logic at `packages/elm-cem/bin/split.js:204`). For elm-m3e this materialises
as `packages/elm-m3e/src/M3e/Review/Facts.elm`, 1988 lines, **130 components**. `Cem.Facts` itself
is a zero-dependency package (`jackhp95/elm-cem-facts`, at `packages/elm-cem/facts/`) that depends
only on `elm/core`.

> **A note on counts.** This spec says 130 when describing the workspace tree (counted:
> `grep -c '{ component = "'` on the file above) and 129 when quoting `Builder.elm`'s own
> verification notes, which were written against the copy vendored into `avetta/ui`. The
> discrepancy is a snapshot difference, not a disagreement, and it is a small illustration of why
> Compose must read the facts it is compiled against rather than hardcode anything about them.

So the whole of Compose's *logic* can be written against `List Fact` and nothing else. Only its
*rendering* and its *value-setter dispatch* are library-specific.

### 1.2 Naming

The workspace already contains a published package named `jackhp95/elm-m3e-builder`
(`packages/elm-m3e/elm-m3e-builder/elm.json`), which is the ~130-module `M3e.Build.*` phantom
pipeline surface and has nothing to do with this feature. The ancestor prototype is also called
`Builder`. **"Compose" is therefore the name, and "Builder" must not be reused** for this feature
at any layer — package, module, or route.

## 2. Motivation & prior art

### 2.1 The problem

`elm-m3e` exposes 130 components across five facets. The typed API makes invalid states
unrepresentable, which is the point — but it also means a newcomer's first question ("what can go
inside an `m3e-list-item`?") is answered by a type error rather than by an affordance. The docs app
today (`packages/elm-m3e/docs/`) has 40 routes, all of which show *hand-authored* examples. There
is no route where a user can assemble a component tree themselves, and no route driven by
`M3e.Review.Facts` at all.

### 2.2 External prior art

**GraphiQL Explorer** (<https://github.com/OneGraph/graphiql-explorer>,
<https://www.npmjs.com/package/@graphiql/plugin-explorer>) is the closest analog and the strongest
evidence the interaction works. It walks a GraphQL schema, rendering checkboxes for leaf fields
and expand-arrows for object fields; checking and expanding builds a real, valid query in an
adjacent pane, live. The structural correspondence to Compose is near-exact: schema type
information determines what is offered, each selection incrementally reveals the next level of
nested structure, and the output is real generated syntax rather than a description of it. Compose
substitutes `Cem.Facts` for the GraphQL introspection schema and an element tree for a query
document.

**Storybook Controls** (<https://storybook.js.org/docs/essentials/controls>) auto-generates a typed
form from a component's prop types — a `select` for enums, a checkbox for booleans, a text input
for strings. It is flat: one component at a time, no recursion. Its architectural relevance is
different and more important than its UI: Storybook's *core* is design-system-agnostic, and the
actual control widgets are supplied by the consuming project. That split — generic engine,
consumer-owned widgets — is exactly the split Compose adopts in §4.

**Hazel / Hazelnut** (<https://hazel.org/>, POPL'17) is the intellectual lineage rather than a UI to
copy. Hazel is a structure editor in which the cursor only ever occupies well-typed positions and
every edit action is type-directed, so the program is well-typed at every intermediate state.
Compose's invariant is the same shape, one rung down the ladder of ambition: every tree Compose can
represent is a tree the facts say is legal, because there is no keystroke that can produce an
illegal one. Hazel's later *livelits* work — plugging bespoke GUIs into typed holes — is
conceptually the chip→menu pattern: a slot is a hole, and the menu is the type-directed way to fill
it.

**Notion**'s database-property chips and **Figma**'s variant/property panel are the right *visual*
references for "click a chip, get a menu of legal values." Neither is schema-recursive: Notion's
property set is flat per row, and Figma's panel configures one selected node. Cite them for the
affordance, not the architecture.

### 2.3 Prior art in this codebase family — the direct ancestor

`/Users/jhp/code/avetta/ui.tw4-pr6-play/src/elm/App/Play/Builder.elm` (1736 lines) is a working,
shipped, single-component version of this idea. It lives in the `avetta/ui` application repo and is
**not portable** — it imports `M3e`, `M3e.Attributes`, `M3e.Values`, `M3e.Review.Facts`, and
`TypedHtml` directly. What it establishes, and what Compose inherits:

| Mechanism | Where | What Compose does with it |
|---|---|---|
| `tagFor` / `toKebabCase` — `"appBar"` → `"m3e-app-bar"` | `Builder.elm:437-454` | Moves to the **consumer**; the prefix and casing rule are library-specific. |
| Generic render via `Html.node (tagFor fact.component) attrs children` | `renderSelected`, `Builder.elm:676-686` | Becomes the consumer's recursive `renderNode`. Verified to match `M3e.Html`'s own tag literals for all 129 components. |
| `slotInfos` — union of `requiredSlots`, `multiSlots`, and `slotKinds` keys | `Builder.elm:473-492` | Moves into the **core** verbatim; it is pure `Fact` arithmetic. |
| `slotContentKind` — text/html/link kinds beat a nested-component kind; `shared:icon` is its own kind | `Builder.elm:505-524` | **Not ported.** Its winner-takes-all precedence is replaced by non-exclusive `SlotAffordances` (§6.5, decision §8.7). The core still reads the same `kinds` tokens; it just stops discarding all but one. |
| `nonEnumAttrNames` — `attrRewrites` values, minus enum names, minus unclassifiable names | `Builder.elm:576-587` | Splits: the set arithmetic goes to the core, the `classify` call becomes injected data (§5.3). |
| `App.Play.Builder.Attrs.classify` — a 1716-line mechanically-derived name→`AttrKind` table | `Builder/Attrs.elm` | Stays in the **consumer**. It names real `M3e.Attributes` functions so a renamed setter is a compile error, which is only possible in a module that can import them. |
| `codeSnippet` / `attrCodeLine` / `slotCodeLine` | `Builder.elm:770-856` | Becomes the consumer's recursive codegen fold. |
| `renderDefaultInstance` — depth-capped auto-fill of required nested slots | `Builder.elm:728-763` | **Deleted.** See §8. |

And what it is not: `Builder.elm` configures exactly one component. Its only nesting is
`renderDefaultInstance`, a non-interactive, depth-capped, defaults-only filler that exists so a
preview of `accordion` is not visibly empty. The user cannot select what goes in a nested slot,
cannot configure it, and cannot nest a third level. **Generalising that one hardcoded level into
unbounded, user-driven recursive editing is the entire value proposition of Compose.**

## 3. Non-goals

Explicitly out of scope for this POC. Each is deferrable without redesigning the core.

1. **Drag-to-reorder children.** Children are appended and removed by index. Reordering needs a
   `MoveChild` message and a drag interaction; neither changes the data model, so it can be added
   later without touching anything else.
2. **Persistence or sharing of a built tree.** No URL serialisation, no localStorage, no
   encoder/decoder for `Node`. A page reload starts from an empty root. (Note that `Builder.elm`
   *does* have URL round-tripping via `?component=` and `withSelected` — Compose deliberately does
   not inherit it, because serialising a recursive tree into a URL is a real design problem and not
   the one being answered here.)
3. **Writing a second adapter.** Portability is demonstrated by the *shape* of the dependency graph
   — the core compiles against `elm-cem-facts` and `elm/core` only, so it cannot have absorbed
   anything M3e-specific — and by the core's test suite running on hand-written fake facts (§13).
   Actually standing up a Compose route for a second `elm-cem` brand is future work.
4. **Undo/redo.** No edit history.
5. **Validation reporting.** Compose prevents illegal trees by construction; it does not *report*
   on them. There is no "this required slot is empty" warning surface. A required slot is marked
   `required` in its chip info and the consumer may style it, but nothing blocks or complains.
6. **Event handlers.** `attrRewrites` entries whose setters live in `<Brand>.Events` (`onClick`,
   `onChange`, …) are not configurable. `Builder.elm` excludes them via `classify` returning
   `Nothing`; Compose inherits that exclusion through the injected kind table (§5.3).
7. **Editing the facts.** Compose is read-only with respect to `Fact`. It is not a manifest editor.
8. **The `Facet` dimension.** `Fact.facets` records which of the five facets (`Raw`/`Html`/
   `Standard`/`Record`/`Build`) a component emits at. Compose targets exactly one facet for
   codegen, chosen by the consumer, and ignores the rest. There is no facet switcher (contrast
   `Doc.Usage`, which has a four-tab surface switcher — that is a different feature).
9. **Non-slot children.** Text and icon content are supported (§5.5) because most slots want them;
   arbitrary raw HTML is not.

## 4. Architecture: the headless split

```
┌────────────────────────────────────────────────────────────────┐
│  packages/elm-cem-compose/          jackhp95/elm-cem-compose   │
│  type: package                                                  │
│                                                                 │
│  deps: elm/core, jackhp95/elm-cem-facts, elm-community/list-extra│
│  NO elm/html.  NO TypedHtml.  NO HtmlIr.  NO M3e.               │
│                                                                 │
│  Owns:  Node / Child / AttrValue / Path                         │
│         update : Msg -> Model -> Model                          │
│         pure query functions (attrChips, slotChips, …)          │
│  Renders: nothing.                                              │
└────────────────────────────────────────────────────────────────┘
                              ▲
                              │ imports Cem.Compose
                              │ calls queries, sends Msgs
┌─────────────────────────────┴──────────────────────────────────┐
│  packages/elm-m3e/docs/app/Route/Components/Compose.elm         │
│  (an elm-pages route in a type: application)                    │
│                                                                 │
│  deps: Cem.Compose + M3e.* + TypedHtml + M3e.Review.Facts       │
│                                                                 │
│  Owns:  100% of the view — cards, chips, menus                  │
│         the attr-kind dispatch table (name -> AttrKind)         │
│         tagFor / kebab-casing                                   │
│         the live renderNode fold                                │
│         the codegen fold                                        │
└────────────────────────────────────────────────────────────────┘
```

The core renders nothing. It owns Fact-derived state, path-addressed edit logic, and pure query
functions. The consumer writes every pixel.

**The one piece of UI state the core does own is `openMenu`** — which chip's menu is currently
open. This looks like a layering violation and is not: *which options a menu contains* depends on
the `Fact`, which is unambiguously the core's domain, and the core must therefore know which menu
is being asked about in order to answer. Splitting "the menu is open" (consumer) from "here is what
is in it" (core) would force the consumer to pass the path and menu kind back into every query on
every render, which is the same coupling with more ceremony. Rendering the menu remains the
consumer's job entirely; the core just says which one is live.

### 4.1 Why the consumer must own attribute dispatch

Elm has no reflection. A `Fact` describes an attribute only as a `String` — `"variant"` — while
`M3e.Attributes.variant` is an ordinary Elm function with its own parameter type. There is no way
to go from the string to the call. `Builder/Attrs.elm` solves this with a 1716-line lookup table,
one branch per setter name and, for enums, one per accepted token, calling each setter *for real*
so that a removed setter or an invalid token is a **compile error in that table** rather than a
silent no-op at runtime. Its module doc records the verification: all 201 distinct (attribute,
token) enum pairs and all 182 non-enum setter names used across the 129 components resolve to a
real setter.

That table cannot live in the core, because it imports the library. It is the single largest piece
of per-library adapter work, it is mechanically derivable, and it is where the type-safety of the
whole feature actually lives. The core's job is to know *that* an attribute is boolean-shaped; the
consumer's job is to know *which function to call*.

## 5. Core data model

Module `Cem.Compose`, the package's single exposed module.

### 5.1 `AttrValue`

Generalises `Builder.elm`'s five separate choice maps (`enumChoices`, `boolChoices`,
`stringChoices`, `floatChoices`, `intChoices` — `Builder.elm:216-228`) into one value type.

```elm
type AttrValue
    = AttrBool Bool
    | AttrString String
    | AttrFloat String
    | AttrInt String
    | AttrEnum String
```

**Numeric values carry raw entry text, not `Float`/`Int`.** This is deliberate and copied from
`Builder.elm:222-223`, where `floatChoices`/`intChoices` are `Dict String String`. If the model
stored a parsed number, a user mid-typing `"1."` or `"-"` would have the character eaten on every
keystroke. The text is parsed with `String.toFloat` / `String.toInt` at the point of use, and an
unparseable value simply contributes no attribute — matching `buildNonEnumAttr`
(`Builder.elm:633-641`), which uses `Maybe.andThen` over the parse.

`AttrFloat` and `AttrInt` are distinct variants even though both hold `String`, because codegen
must emit `String.fromFloat` vs `String.fromInt` shapes and the consumer's dispatch table has
separate `setFloatAttr` / `setIntAttr` entries.

### 5.2 `AttrKind`

```elm
type AttrKind
    = BoolAttr
    | StringAttr
    | FloatAttr
    | IntAttr
```

Deliberately identical to `App.Play.Builder.Attrs.AttrKind` (`Builder/Attrs.elm:44-49`). Enum-ness
is not a member of this type: whether an attribute is an enum is already answered by whether its
name appears in `fact.enums`, which the core reads directly.

### 5.3 The injected kind table — *a refinement of the approved design*

> **This is an addition, flagged for review.** The brainstorming design said `attrChips` returns one
> entry per "enum/bool/string/float/int attr the node's Fact exposes." A `Fact` does not contain
> that information. It has `enums : List (String, List String)` and `attrRewrites : List (String,
> String)`, and nothing that says whether `"disabled"` is a `Bool` or a `String`. `Builder.elm` gets
> it from `App.Play.Builder.Attrs.classify`, a library-specific table. The core therefore cannot
> derive attribute kinds and must be given them.

The core takes the table as **data, not a function**:

```elm
attrKinds : Dict String AttrKind
```

carried on the `Model` and supplied by the consumer at `init`. Data rather than a
`String -> Maybe AttrKind` function because a function in the model defeats `==`, breaks
`Debug.log`, and blocks `Html.Lazy`; a `Dict` has none of those problems and is trivially
constructible in a test.

An attribute name absent from this `Dict` and absent from `fact.enums` is **not offered as a chip
at all** — exactly reproducing `Builder.elm:585`'s
`List.filter (\name -> Attrs.classify name /= Nothing)`, which is how event setters like `onClick`
are excluded (non-goal 6).

The consumer builds this once, at the top level, from its own mechanically-derived table:

```elm
-- in the consumer
attrKinds : Dict String Cem.Compose.AttrKind
attrKinds =
    M3e.Review.Facts.facts
        |> List.concatMap (.attrRewrites >> List.map Tuple.second)
        |> List.filterMap (\name -> Maybe.map (Tuple.pair name) (classifyToCompose name))
        |> Dict.fromList
```

### 5.4 `Node`

```elm
type Node
    = Node
        { component : String
        , attrs : Dict String AttrValue
        , children : Dict String (List Child)
        }
```

The `type` wrapper is not stylistic — Elm cannot express a recursive `type alias`, so a
`Cem.Compose`-owned custom type is required for `Node` to contain `Node`s.

> **Divergence from the brainstorming sketch, flagged.** That sketch listed both
> `attrs : Dict String AttrValue` *and* `enumChoices : Dict String String`. These are redundant
> once `AttrValue` has an `AttrEnum` variant — which the same sketch asked for, in the instruction
> to fold "the four `Dict String X` choice maps plus `enumChoices` into one value type per attr."
> Keeping both would create two places to look for an enum's current value and two places for them
> to disagree. **Resolved by collapsing: `enumChoices` is gone, enums live in `attrs` as
> `AttrEnum`.** No behaviour is lost.

`children` is keyed by slot name, mirroring the union of a `Fact`'s `requiredSlots`, `multiSlots`,
and `slotKinds` keys. Each slot holds an **ordered list**. A slot listed in `fact.multiSlots` may
hold any number; every other slot is capped at one, and this cap is a **model invariant maintained
by `update`, not merely a convention** — `AddChild` on a filled non-multi slot replaces index 0
rather than appending. This parallels `Builder.elm`'s treatment of a slot as having exactly zero or
one occupant (`slotEnabled : Dict String Bool`, `Builder.elm:225`).

The invariant is why `Node` is **opaque**: the constructor is not exposed, so no consumer can build
a two-element non-multi slot. Accessors (§6.6) give the consumer everything its three folds need.

### 5.5 `Child` — *a refinement of the approved design*

> **This is the one substantive extension to the approved model.** The brainstorming design said
> `children : Dict String (List Node)`. That cannot represent a text or icon slot, and text slots
> are not an edge case: most slots in the library name `"shared:text"` (or `"html"`, or
> `"shared:link"`) among their `kinds`, and an empty `kinds` — documented in `Cem.Facts` as
> "unconstrained" — is text-fillable too. A `List Node`-only model would leave most slots in most
> components unfillable, and the tool would be unusable for exactly the components a newcomer
> reaches for first (`button`'s label, `list-item`'s headline).

```elm
type Child
    = ChildNode Node
    | ChildText String
    | ChildIcon String
```

**This variant type is where a slot's content mode is decided, and the decision is made at *choice*
time, not ahead of it.** A slot is no longer pre-classified into one permitted mode: it advertises
every mode its `kinds` allow (§6.5), the user picks one from the slot's menu, and the picked option
determines which `Child` variant is constructed. `AddTextChild` builds a `ChildText`,
`AddIconChild` a `ChildIcon`, `AddChild` a `ChildNode` — and for most slots more than one of those
three messages is legal, which is the whole point of decision §8.7. The same slot on the same
component can therefore hold a text child in one tree and a nested component in another.

The three variants happen to be a one-to-one image of `Builder.elm`'s `SlotContentKind`
(`TextSlot | IconSlot | NestedSlot String`), so no new *concept* is introduced — but the prototype
used that type to pick one mode per slot and forbid the other two, whereas here it is a tagged union
of what a child actually *is*. That is the difference between a constraint and a representation.

`ChildIcon` holds a Material Symbols glyph name (`Builder.elm` defaults it to `"star"`,
`Builder.elm:719`). The core treats it as an opaque `String`; it does not know what an icon is.

**Rejected alternative:** keep `List Node` and represent text as a `Node` with a core-reserved
sentinel component name such as `"@text"`, carrying the content in `attrs`. This preserves the
approved type at the cost of a stringly-typed magic value that every consumer fold must special-
case, that can collide with a real component name in some future brand, and that makes the
`children` type a lie. Rejected. Recorded here so the choice can be overruled cheaply if the
sentinel is preferred.

### 5.6 Addressing

```elm
type PathStep
    = IntoSlot String Int


type alias Path =
    List PathStep
```

A `Path` is read root-first. `[]` is the root node. `[ IntoSlot "unnamed" 0 ]` is the first child of
the root's default slot. The `Int` indexes the slot's `List Child`.

```elm
updateAt : Path -> (Node -> Node) -> Node -> Node
```

The single recursive locator. Every structural edit goes through it. It descends only through
`ChildNode`; a path step landing on a `ChildText` or `ChildIcon`, or on an out-of-range index, or
on a slot name with no entry, is a **no-op** — `updateAt` returns the tree unchanged. Compose never
crashes on a stale path, which matters because the consumer holds paths across renders and a
`RemoveChild` can invalidate a sibling's index.

### 5.7 `MenuKind` and `Model`

```elm
type MenuKind
    = AttrMenu String
    | SlotMenu String


type alias Model =
    { root : Node
    , facts : Dict String Fact
    , attrKinds : Dict String AttrKind
    , openMenu : Maybe ( Path, MenuKind )
    }
```

`facts` is a `Dict` keyed by `Fact.component`, not the `List Fact` the generated module exposes,
because every query does a lookup — the same indexing `Builder.elm:250-252` does with
`factByName`. `init` performs the fold.

**The root cannot be deleted.** `RemoveChild` addresses a child by (parent path, slot, index), so
there is no message that can remove the root — it has no parent to be removed from. The root can be
reconfigured freely (attributes set, children added and removed); it cannot be destroyed, and it
cannot be replaced with a different component. Changing which component the root is means calling
`init` again.

### 5.8 `Msg`

```elm
type Msg
    = SetAttr Path String AttrValue
    | ClearAttr Path String
    | OpenMenu Path MenuKind
    | CloseMenu
    | AddChild Path String String
    | AddTextChild Path String
    | AddIconChild Path String
    | SetChildContent Path String Int String
    | RemoveChild Path String Int
```

| Message | Arguments | Meaning |
|---|---|---|
| `SetAttr` | node path, attr name, value | Set one attribute on the node at `path`. Closes any open menu. |
| `ClearAttr` | node path, attr name | Unset it — the chip returns to plain. Closes any open menu. |
| `OpenMenu` | node path, which chip | Record that this chip's menu is live. |
| `CloseMenu` | — | Dismiss. |
| `AddChild` | parent path, slot name, component name | Append (or, on a filled non-multi slot, replace) a fresh empty `ChildNode`. |
| `AddTextChild` | parent path, slot name | Append/replace a `ChildText ""`. |
| `AddIconChild` | parent path, slot name | Append/replace a `ChildIcon "star"`. |
| `SetChildContent` | parent path, slot, index, text | Set the payload of a `ChildText`/`ChildIcon`. No-op on a `ChildNode`. |
| `RemoveChild` | parent path, slot, index | Drop that child and its whole subtree. |

`AddChild` with a component name absent from `Model.facts` is a **no-op** rather than an error, for
the same reason `slotMenuOptions` omits such names (§6.5) — the two must agree, or the menu could
offer an option that does nothing.

The three `Add*Child` messages are siblings, not alternatives selected by the slot: which of them
the consumer may send for a given slot is answered by that slot's `SlotAffordances` (§6.5), and for
most slots more than one is permitted. `AddTextChild` / `AddIconChild` on a slot whose affordances
do not allow text / icons is a **no-op**, on the same agree-with-the-menu principle.

`SetAttr` deliberately does not validate that the value's variant matches the attribute's kind.
Doing so would require returning a `Result` and would only catch a consumer bug that the consumer's
own typed dispatch table already catches at compile time.

## 6. Core API surface

Every function below is pure, `Html`-free, and total. Full signatures.

### 6.1 Construction and update

```elm
init :
    { facts : List Fact
    , attrKinds : Dict String AttrKind
    , root : String
    }
    -> Model
```

`root` is the component name the empty tree starts at. If it is not among `facts`, the model is
still constructed — every query on it returns empty, and the consumer renders a card with no chips.
This mirrors `Builder.elm:402-404`'s posture that an unknown selection "is applied verbatim and is
harmless," degrading to an empty state rather than a crash.

```elm
update : Msg -> Model -> Model
```

No `Cmd`, no `Effect`. Compose's core has no side effects of any kind: no HTTP, no navigation, no
ports. (`Builder.elm` returns an `Effect` solely to push `?component=` into the URL, which is
non-goal 2.) Every structural message applies `updateAt` and then sets `openMenu = Nothing` —
selecting a value dismisses its menu, which is §7's cycle.

### 6.2 Navigation

```elm
nodeAt : Path -> Model -> Maybe Node
```

`Nothing` for any path that does not resolve to a `ChildNode` (out of range, wrong slot, or landing
on text/icon content).

```elm
factAt : Path -> Model -> Maybe Fact
```

Convenience: `nodeAt` then `Dict.get` on `facts`. `Nothing` if either step fails. The consumer
needs the `Fact` at nearly every node to render the card header, so it is worth not making every
caller write the two-step.

### 6.3 Attribute chips

```elm
type alias AttrChipInfo =
    { name : String
    , kind : AttrChipKind
    , isSet : Bool
    , currentValue : Maybe AttrValue
    }


type AttrChipKind
    = EnumChip (List String)
    | PlainChip AttrKind
```

```elm
attrChips : Path -> Model -> List AttrChipInfo
```

One entry per configurable attribute the node's `Fact` exposes. Empty list for an unresolvable
path.

> **Minor addition to the approved shape, flagged.** The brainstorming design specified
> `{ name, isSet, currentValue }`. `kind` is added because the consumer cannot render a chip
> without it — an enum chip's label shows the current token, a boolean chip is a toggle, and a
> string chip opens a text field. Without `kind` the consumer would have to call
> `attrMenuOptions` for every chip on every render just to discover its shape, which is the same
> information at higher cost. Purely additive; nothing in the approved fields changes.

Composition, generalising `fact.enums ++ nonEnumAttrNames fact` (`Builder.elm:576-587`):

1. **Enum chips** — one per `fact.enums` entry, in the `Fact`'s own order, carrying its token list.
2. **Plain chips** — `fact.attrRewrites |> List.map Tuple.second`, minus any name already in
   `fact.enums`, minus any name absent from `Model.attrKinds`, deduplicated and sorted. The dedup
   and sort reproduce `Builder.elm:586-587`'s `Set.fromList >> Set.toList`; `attrRewrites` maps
   *barrel* setter name to *per-component* setter name and the same per-component name can be
   reached from more than one barrel entry, so deduplication is required, not cosmetic.

The order is deterministic (fact order, then alphabetical) so the chip-set does not reshuffle
between renders.

`isSet` is `True` exactly when `name` has an entry in the node's `attrs`. **This is a deliberate
behavioural change from `Builder.elm`, which has no unset state for enums:** `currentEnum`
(`Builder.elm:590-593`) falls back to the first token, and `buildAttrsFromModel`
(`Builder.elm:650-653`) emits every enum unconditionally, so a `Builder` preview always carries
every enum attribute whether or not the user chose it. Compose needs a genuine unset state, because
"plain chip vs filled chip" *is* the interface, and because a snippet that sets every enum to its
first token is not the snippet the user built. An unset attribute contributes nothing to the
preview and nothing to the generated code.

### 6.4 Attribute menus

```elm
type NumberKind
    = FloatNumber
    | IntNumber


type MenuOptions
    = EnumTokens (List String) (Maybe String)
    | BoolToggle Bool
    | TextInput String
    | NumberInput NumberKind String
```

```elm
attrMenuOptions : Path -> String -> Model -> Maybe MenuOptions
```

What to draw for the attribute named by an open `AttrMenu`. `Nothing` if the path does not resolve,
or if the attribute is not one this node offers.

`EnumTokens` carries the legal tokens plus the currently-selected one (`Nothing` when unset).
`BoolToggle`, `TextInput`, and `NumberInput` carry the current value — booleans default to `False`
and text to `""` when unset, matching `currentBool` / `currentString` (`Builder.elm:596-613`). The
consumer decides whether a boolean is a switch, a checkbox, or two menu items; the core only says
it is boolean-shaped and what it currently is.

### 6.5 Slot chips and menus

```elm
type alias SlotAffordances =
    { text : Bool
    , icon : Bool
    , components : List String
    }


type alias SlotChipInfo =
    { name : String
    , required : Bool
    , affordances : SlotAffordances
    , filled : Int
    , max : Maybe Int
    }
```

```elm
slotChips : Path -> Model -> List SlotChipInfo
```

One entry per slot the `Fact` declares. The slot set is
`fact.requiredSlots ++ fact.multiSlots ++ List.map Tuple.first fact.slotKinds`, deduplicated —
`slotInfos`, `Builder.elm:473-492`, moved into the core unchanged. Order is deterministic:
required slots first (in `requiredSlots` order), then the rest alphabetically.

- `required` — `List.member name fact.requiredSlots`.
- `affordances` — **every content mode the slot's `kinds` permit, not the highest-precedence one.**
  This replaces `Builder.elm`'s `slotContentKind` (`Builder.elm:505-524`) rather than porting it;
  see decision §8.7. Derived from the slot's `kinds` in `fact.slotKinds`:
  - `text` — `True` when `kinds` is empty (`Cem.Facts` documents empty as *unconstrained*), or when
    `kinds` contains any of `"html"`, `"shared:text"`, `"shared:link"`, `"shared:flow"`,
    `"shared:phrasing"`. The last two are HTML content categories that the inherited rule did not
    name at all and let fall through to its component branch, which was a latent bug; they are
    text-shaped and are classified as such here.
  - `icon` — `True` when `kinds` contains `"shared:icon"`.
  - `components` — every `kinds` entry that is a bare component noun (no `":"`), **filtered to names
    present in `Model.facts`**, deduplicated, in `kinds` order. Measured against the real bundle:
    every noun resolves, so the filter never fires today (§14, risk 2).

  The three are independent. A slot may have all of them (`button.unnamed`: text, icon, and 15
  components), exactly one (`list.unnamed`: 5 components, no text), or — for a slot whose `kinds`
  resolve to nothing offerable — none, in which case its chip is inert and the consumer should
  render it disabled.
- `filled` — current child count.
- `max` — `Nothing` for a slot in `fact.multiSlots`; `Just 1` otherwise. This is the machine-
  readable form of the replace-not-append invariant, so the consumer can label the chip
  ("2", "1 / 1") without re-deriving it.

**Unconstrained still does not mean "offer every component."** An empty `kinds` yields
`{ text = True, icon = False, components = [] }`: a 130-item menu is not an affordance, and the
facts give no basis for ranking such a list. This is the one place the old rule's outcome is
retained, now as a deliberate narrow choice rather than a side effect of precedence.

```elm
type SlotOption
    = OptionText
    | OptionIcon
    | OptionComponent String


slotMenuOptions : Path -> String -> Model -> List SlotOption
```

**The full menu for a slot: every valid way to fill it, in one list.** This is the query the chip's
popup is drawn from, and it is the API-level expression of decision §8.7 — it enumerates, where the
previous design collapsed.

Derived directly from that slot's `SlotAffordances`, in a fixed order so the menu does not
reshuffle between renders:

1. `OptionText`, if `affordances.text`;
2. `OptionIcon`, if `affordances.icon`;
3. one `OptionComponent name` per entry of `affordances.components`, in that field's order.

Text and icon lead because they are the cheap, terminal choices; the component list is the branch
into recursion. Returns `[]` — an inert chip — only when the slot affords nothing at all.

Each option maps to exactly one message: `OptionText` → `AddTextChild`, `OptionIcon` →
`AddIconChild`, `OptionComponent n` → `AddChild … n`. The consumer needs no other query to build the
popup, and **no option in this list is ever a no-op**, which is the invariant §15 tests for.

For a slot whose `kinds` name a component the facts do not contain, that name is **silently
omitted** from `affordances.components` and so from the menu. This was an explicit decision in the
brainstorming conversation, taken over surfacing a visible "facts data problem" banner, in order to
keep the POC's error-handling surface small. It matches the existing posture at
`Builder.elm:703-708`, where `renderDefaultInstance`'s `Dict.get nestedComponent factByName`
returning `Nothing` yields `[]`. The consequence is that a malformed or partial facts bundle
degrades to a shorter menu with no diagnostic. §14, risk 2 records the cost.

### 6.6 Accessors for the consumer's folds

`Node` is opaque, so the three consumer folds (§9) need read access.

```elm
componentOf : Node -> String
attrsOf : Node -> List ( String, AttrValue )
slotsOf : Node -> List ( String, List Child )
```

`attrsOf` and `slotsOf` return sorted association lists (`Dict.toList` order) so that two equal
trees always produce byte-identical generated code — a snapshot-testable property.

`slotsOf` returns only slots that currently hold children. A fold that needs the full declared slot
set, filled or not, asks `slotChips`.

## 7. Interaction cycle

One cycle, identical for every `elm-cem` library:

```
 user clicks a chip
   → consumer sends  OpenMenu path (AttrMenu name)   [or SlotMenu name]
   → core sets       Model.openMenu = Just (path, kind)
   → consumer re-renders, sees openMenu matches this card + chip,
     calls attrMenuOptions / slotMenuOptions to draw the popup
   → user picks an option
   → consumer sends  SetAttr path name value          [or AddChild / AddTextChild / …]
   → core edits the tree at path via updateAt, sets openMenu = Nothing
   → consumer re-renders: chip is now filled, preview and snippet reflect the edit
```

### 7.1 Trace A — setting an enum attribute

Start: `init { facts = M3e.Review.Facts.facts, attrKinds = …, root = "button" }`.

```elm
Model
    { root = Node { component = "button", attrs = Dict.empty, children = Dict.empty }
    , openMenu = Nothing
    , … }
```

1. The consumer renders one card. `attrChips [] model` reads the real `button` fact
   (`packages/elm-m3e/src/M3e/Review/Facts.elm:211-224`), whose `enums` are

   ```elm
   [ ( "shape", [ "rounded", "square" ] )
   , ( "size", [ "extraLarge", "extraSmall", "large", "medium", "small" ] )
   , ( "type_", [ "button", "reset", "submit" ] )
   , ( "variant", [ "elevated", "filled", "outlined", "text", "tonal" ] )
   ]
   ```

   giving four enum chips, then plain chips from `attrRewrites` — `disabled`,
   `disabledInteractive`, `download`, `href`, `name`, `rel`, `selected`, `target`, `toggle`,
   `value`, `defaultSelected`, `defaultValue`. Note what is *dropped*: `shape`, `size`, `type_`,
   and `variant` appear in `attrRewrites` too and are excluded as already-enum chips, and
   `onBeforeinput`, `onInput`, `onChange`, `onClick` are excluded because they are absent from
   `attrKinds` (non-goal 6). The `variant` chip is
   `{ name = "variant", kind = EnumChip [ "elevated", "filled", "outlined", "text", "tonal" ]
   , isSet = False, currentValue = Nothing }`, drawn as a plain (unfilled) `m3e-filter-chip`.

2. User clicks it. Consumer fires `OpenMenu [] (AttrMenu "variant")`.

3. Core: `openMenu = Just ( [], AttrMenu "variant" )`. Nothing else changes.

4. Consumer re-renders. On the root card it sees `openMenu` matches `( [], AttrMenu "variant" )` and
   calls `attrMenuOptions [] "variant" model`, receiving
   `Just (EnumTokens [ "elevated", "filled", "outlined", "text", "tonal" ] Nothing)`. It draws an
   `m3e-menu` with five items, none marked current.

5. User picks `filled`. Consumer fires `SetAttr [] "variant" (AttrEnum "filled")`.

6. Core: `updateAt [] (setAttr "variant" (AttrEnum "filled")) root`, then `openMenu = Nothing`.

```elm
Node { component = "button"
     , attrs = Dict.fromList [ ( "variant", AttrEnum "filled" ) ]
     , children = Dict.empty }
```

7. Consumer re-renders. `attrChips` now reports
   `{ name = "variant", isSet = True, currentValue = Just (AttrEnum "filled"), … }` → filled chip.
   `renderNode` emits `<m3e-button variant="filled">`. Codegen emits
   `M3e.Attributes.variant M3e.Values.filled`.

### 7.2 Trace B — adding a nested child two levels deep

Continuing from Trace A. Goal: put an icon in the button's `icon` slot, then build a `list` whose
first `listItem` has a text headline.

1. `slotChips [] model` reads the real `button` fact's slots. Its `requiredSlots` is `[ "unnamed" ]`,
   its `multiSlots` is `[]`, and its `slotKinds` names five slots. Required first, then
   alphabetical:

   | chip | `required` | `kinds` (abridged) | `affordances` | `max` |
   |---|---|---|---|---|
   | `unnamed` | ✅ | 15 component nouns + `shared:icon` + `shared:text` | text ✅, icon ✅, 15 components | `Just 1` |
   | `icon` | — | `loadingIndicator`, `shared:icon` | text —, icon ✅, `[ "loadingIndicator" ]` | `Just 1` |
   | `selected` | — | `heading`, `shared:icon`, `shared:text` | text ✅, icon ✅, `[ "heading" ]` | `Just 1` |
   | `selected-icon` | — | `shared:icon` | text —, icon ✅, `[]` | `Just 1` |
   | `trailing-icon` | — | `shared:icon` | text —, icon ✅, `[]` | `Just 1` |

   `unnamed` now offers all 17 of its options rather than collapsing to a text box. Under the
   precedence rule superseded by §8.7 — stated at §14, risk 3 — `shared:text` would have won and all
   15 nested components would have been unreachable. This is the sharpest single illustration of why
   that rule was replaced.

2. User clicks the `icon` chip. `slotMenuOptions [] "icon" model` returns
   `[ OptionIcon, OptionComponent "loadingIndicator" ]` — a two-item menu, where the old design
   would have silently committed the slot to an icon and hidden the loading indicator. The user
   picks the icon. Consumer fires `AddIconChild [] "icon"` and renders an inline text field for the
   glyph name.

```elm
children = Dict.fromList [ ( "icon", [ ChildIcon "star" ] ) ]
```

   Note the `selected-icon` and `trailing-icon` chips, whose only affordance is `OptionIcon`. A
   one-item menu is a pointless click, so the consumer is free to fire `AddIconChild` directly when
   `slotMenuOptions` returns a single option. That is a consumer-side shortcut over a uniform core
   answer, not a special case in the core.

3. User types `favorite`. Consumer fires `SetChildContent [] "icon" 0 "favorite"` →
   `ChildIcon "favorite"`. Preview: `<m3e-icon slot="icon">favorite</m3e-icon>`.

4. Now the recursive case. Re-init the root as `"list"`. The real `list` fact
   (`Facts.elm:811-821`) has `multiSlots = [ "unnamed" ]` and
   `slotKinds = [ ( "unnamed", [ "divider", "expandableListItem", "listAction", "listItem",
   "listOption" ] ) ]` — five component nouns and **no** `shared:*` kind, so its affordances are
   `{ text = False, icon = False, components = [ … 5 … ] }`. `slotChips [] model` gives
   `{ name = "unnamed", required = False, affordances = that, filled = 0, max = Nothing }`. This is
   a pure-nesting slot: unlike `button.unnamed` it offers no text at all, so the menu is
   components-only.

5. User clicks it. Consumer fires `OpenMenu [] (SlotMenu "unnamed")`.

6. Consumer re-renders, calls `slotMenuOptions [] "unnamed" model` →
   `[ OptionComponent "divider", OptionComponent "expandableListItem", OptionComponent "listAction",
   OptionComponent "listItem", OptionComponent "listOption" ]`. All five exist in `facts`, so none
   is dropped. No `OptionText`, because `list.unnamed` does not accept text. Draws a five-item menu.

7. User picks `listItem`. Consumer fires `AddChild [] "unnamed" "listItem"`.

8. Core appends — `max = Nothing`, so append, not replace — and clears the menu:

```elm
Node { component = "list"
     , attrs = Dict.empty
     , children = Dict.fromList
         [ ( "unnamed"
           , [ ChildNode (Node { component = "listItem"
                               , attrs = Dict.empty
                               , children = Dict.empty }) ]
           ) ]
     }
```

9. Consumer's `viewNode` recurses. At depth 1 it calls `viewNode [ IntoSlot "unnamed" 0 ] …`, which
   calls `attrChips [ IntoSlot "unnamed" 0 ] model` and `slotChips [ IntoSlot "unnamed" 0 ] model`
   against the **`listItem`** fact. A nested card appears inside the root card, with its own chips.
   Nothing about this second card's code differs from the first — it is the same function at a
   longer path.

10. `slotChips` on the `listItem` reads its real fact (`Facts.elm:841-851`): slots `unnamed`,
    `leading`, `overline`, `supporting-text`, `trailing`, none required, none multi, all
    `max = Just 1`. Every one lists `shared:text`, so every one affords text — but every one also
    names at least one component noun, and under the superseded rule that made all five text-only:

    | chip | affordances |
    |---|---|
    | `unnamed` | text ✅, icon —, `[ "heading" ]` |
    | `leading` | text ✅, icon ✅, `[ "avatar", "heading" ]` |
    | `overline` | text ✅, icon —, `[ "heading" ]` |
    | `supporting-text` | text ✅, icon —, `[ "heading" ]` |
    | `trailing` | text ✅, icon ✅, `[ "avatar", "checkbox", "heading", "radio", "switch" ] ` |

    `listItem.trailing` is the case §14's risk 3 named as the indictment of the old rule — *"a user
    cannot put a checkbox in a list item's trailing slot, one of the most ordinary things in the
    entire library."* It now offers `[ OptionText, OptionIcon, OptionComponent "avatar",
    OptionComponent "checkbox", OptionComponent "heading", OptionComponent "radio",
    OptionComponent "switch" ]`, and the checkbox is one click away.

    Here the user wants the plain headline. Clicking `unnamed` opens a two-option menu
    (`OptionText`, `OptionComponent "heading"`); the user picks text. Consumer fires
    `AddTextChild [ IntoSlot "unnamed" 0 ] "unnamed"`, then
    `SetChildContent [ IntoSlot "unnamed" 0 ] "unnamed" 0 "Inbox"`. **The extra click is the whole
    cost of this decision** — where the old design went straight to a text field, the user now
    confirms that text is what they meant. That is the tradeoff §8.7 accepts.

11. Final tree, and the three folds over it:

```elm
-- preview  (the default slot needs no slot= attribute)
<m3e-list>
  <m3e-list-item>
    <span>Inbox</span>
  </m3e-list-item>
</m3e-list>

-- snippet
M3e.Html.list
    [ ]
    [ M3e.Html.listItem
        [ ]
        [ M3e.text "Inbox" ]
    ]
```

The `slot=` attribute is omitted for the slot named `"unnamed"`, which is the facts' name for the
default slot — `slotPlacementAttrs` (`Builder.elm:532-538`) and `slotCodeLine`
(`Builder.elm:841-846`) both special-case it, and both folds must.

12. Clicking the root `list`'s `unnamed` chip again appends a second `listItem` at index 1
    (`max = Nothing`). Clicking the `listItem`'s own `unnamed` chip again **replaces** its existing
    text child (`max = Just 1`) rather than producing two text nodes. Same message, same slot name,
    opposite behaviour — driven entirely by whether the fact lists the slot in `multiSlots`.

### 7.3 Trace C — the stale-path case

User has two children in a multi-slot and removes the first: `RemoveChild [] "unnamed" 0`. The
second child's path silently changes from `[ IntoSlot "unnamed" 1 ]` to `[ IntoSlot "unnamed" 0 ]`.
If `openMenu` was `Just ( [ IntoSlot "unnamed" 1 ], AttrMenu "variant" )`, it now points at nothing.
`update` clears `openMenu` on every structural message, so this exact state is unreachable — but
`updateAt`'s no-op-on-miss contract (§5.6) is what guarantees that a path the consumer holds across
a render can never crash the core even if some future message forgets to clear the menu. Both
belt and braces are intentional; the invariant is cheap and the failure mode it prevents is a
runtime exception in a rendering loop.

## 8. Settled scope decisions

Recorded as settled from the brainstorming conversation, with rationale. Not open questions.

1. **Arbitrary tree depth.** No cap of 2 or 3 levels. This is the actual value proposition over
   `Builder.elm`, whose only nesting is `renderDefaultInstance`'s single hardcoded level. A cap
   would reintroduce the limitation the feature exists to remove.

2. **Both a live preview and a copyable Elm snippet**, not preview-only. `Builder.elm` already
   ships both (`viewPreview`, `viewCodeSnippet`) and the snippet is what makes the tool useful
   beyond the page — the user's actual goal is code in their editor, not a picture.

3. **No auto-filled default instances.** `renderDefaultInstance` (`Builder.elm:728-763`) is not
   ported. Compose always starts from an explicit empty node and the user builds everything by
   hand. Two consequences, both good: the tree on screen is exactly the tree the user made, with no
   phantom content in the snippet that they did not ask for; and, because the only recursion is
   user-driven, **the core needs no depth cap and no recursion guard at all.** `renderDefaultInstance`
   needs its `depth` counter precisely because the facts contain a genuine cycle — measured:
   `navMenuItem` lists `navMenuItem` among its own slot kinds — so an automatic filler would loop
   forever. A human clicking chips cannot loop, and the only bound on tree size is their patience.
   The cycle is a feature for Compose (arbitrarily deep nav menus are buildable) and a hazard only
   for auto-fill, which is why dropping auto-fill removes the need for the guard rather than
   trading one problem for another.

4. **Unknown component names in `slotKinds` are silently omitted** from menu options (§6.5).

5. **The core owns `openMenu`** despite rendering nothing (§4).

6. **One target facet for codegen**, chosen by the consumer (non-goal 8).

7. **A slot's content mode is chosen by the user, per child, not pre-classified per slot.**
   *Decided by the human after this spec's first draft, resolving what §14 recorded as risk 3 and
   as "the most important open question in this spec."* `Builder.elm`'s winner-takes-all
   `slotContentKind` is **not ported**. In its place, `SlotChipInfo` carries `SlotAffordances`
   (`{ text, icon, components }`) and `slotMenuOptions` returns `List SlotOption` enumerating every
   legal way to fill the slot (§6.5). The user picks text, an icon, or a specific nested component
   from that one menu, and the pick determines the `Child` variant (§5.5).

   The decision in the human's words: *"You can pick text, valid named slots, or the unnamed default
   slot elements. Then that submenu will only show the valid options for that slot."*

   Rationale, measured against the real 130-component bundle rather than argued: of the 185 declared
   slots, 108 name at least one real component — and the old rule made **76 of those 108 silently
   text-only**, leaving just 32 reachable. It held the
   library to **29 of 130 components with any reachable nesting**. Enumerating instead of collapsing
   takes that to **66 of 130** — every component that names a component anywhere in its `kinds` — and
   lengthens the longest simple nesting chain from 3 to 5. §14, risk 3 carries the full table.

   The cost is one extra click on slots that afford more than one mode, and a slightly larger menu.
   Both were judged clearly worth it: the feature exists to make nesting discoverable, and a rule
   that hides nesting on 76 slots defeats it.

## 9. Consumer responsibilities

The consumer writes **three independent recursive folds over the same `Node` tree**, plus the
adapter data. None of the three requires any change to the core; that they are three folds over one
structure, rather than three coupled traversals, is the load-bearing property of the design.

### 9.1 Where the route goes

`packages/elm-m3e/docs/app/Route/Components/Compose.elm`, route `/components/compose`.

`docs/app/Route/Components/` currently contains exactly two modules, `All.elm` and `Name_.elm`.
`Name_.elm` is a dynamic segment; adding a static sibling `Compose.elm` is the elm-pages convention
and does not conflict — elm-pages resolves static segments before dynamic ones.

**Template to follow: `docs/app/Route/Examples/Feed.elm`.** It is the cleanest of the ten
`buildWithLocalState` routes in the app: self-owned state, no `BackendTask` data, no deep-linking.

```elm
route : StatefulRoute RouteParams Data ActionData Model Msg
route =
    RouteBuilder.single { head = head, data = BackendTask.succeed {} }
        |> RouteBuilder.buildWithLocalState
            { view = view, init = init, update = update, subscriptions = subscriptions }
```

Compose needs no `BackendTask` at all: unlike `Components/All.elm` and `Components/Name_.elm`, which
load `docs/data/reference.json` via `Doc.Data`, Compose's data source is `M3e.Review.Facts.facts` —
a compiled-in Elm value. `data = BackendTask.succeed {}`.

Signatures, matching the app's shape exactly:

```elm
type alias Model = { compose : Cem.Compose.Model }
type Msg = ComposeMsg Cem.Compose.Msg
type alias RouteParams = {}
type alias Data = {}
type alias ActionData = {}

init : App Data ActionData RouteParams -> Shared.Model -> ( Model, Effect Msg )
update : App Data ActionData RouteParams -> Shared.Model -> Msg -> Model -> ( Model, Effect Msg )
subscriptions : RouteParams -> UrlPath -> Shared.Model -> Model -> Sub Msg
head : App Data ActionData RouteParams -> List Head.Tag
view : App Data ActionData RouteParams -> Shared.Model -> Model -> View (PagesMsg Msg)
```

`update` is a one-liner — `( { model | compose = Cem.Compose.update m model.compose }, Effect.none )`
— because the core returns no effects.

`view` follows the app's convention of erasing the phantom rows once, at the boundary:

```elm
view _ _ model =
    View.fromElement "Compose"
        (M3e.mapMsg PagesMsg.fromMsg
            (M3e.mapMsg ComposeMsg (Doc.pane [ screen model.compose ])))
```

### 9.2 Fold 1 — `viewNode`, the editor

```elm
viewNode :
    Cem.Compose.Path
    -> Cem.Compose.Node
    -> Cem.Compose.Model
    -> Element (M3e.Component.Card.Is s) adm_ Cem.Compose.Msg
```

One `m3e-card` per `Node`. Header names the component. Body is an `m3e-chip-set` built from
`attrChips path model ++ slotChips path model`, then a menu when `model.openMenu` matches this
path, then a recursive call per `ChildNode` in `slotsOf node`.

Sketch:

```elm
viewNode path node model =
    M3e.card [ M3e.Attributes.variant Value.outlined ]
        [ M3e.Component.Card.header
            (Doc.sectionLabel (Cem.Compose.componentOf node))
        , M3e.Component.Card.content
            (TypedHtml.div [ TA.class "flex flex-col gap-3" ]
                [ M3e.chipSet []
                    (List.map (attrChipView path) (Cem.Compose.attrChips path model)
                        ++ List.map (slotChipView path) (Cem.Compose.slotChips path model)
                    )
                , menuFor path model
                , TypedHtml.div [ TA.class "pl-4 flex flex-col gap-3" ]
                    (childCards path node model)
                ]
            )
        ]


attrChipView : Path -> Cem.Compose.AttrChipInfo -> Element … Cem.Compose.Msg
attrChipView path info =
    M3e.filterChip
        [ M3e.Attributes.selected info.isSet
        , M3e.Events.onClick (Cem.Compose.OpenMenu path (Cem.Compose.AttrMenu info.name))
        ]
        [ M3e.text (chipLabel info) ]
```

`filterChip` + `onClick` is exactly the pattern already in `docs/app/Route/Examples/Feed.elm:223`,
so this is not a new interaction shape for the app.

One documented hazard, inherited from `Builder.elm:1274-1305`: `m3e-filter-chip`'s click handler
toggles its own `selected` unconditionally, and `M3e.Attributes.selected` cannot resync a value the
element changed itself. Because Compose's chips are *buttons that open menus* rather than
independently toggleable state, and because every click produces a model change (`OpenMenu` always
changes `openMenu`), the re-click race that bit `Builder.elm`'s type filter does not arise here.
Worth verifying in a browser during the POC rather than assuming.

### 9.3 Fold 2 — `renderNode`, the live preview

```elm
renderNode : Cem.Compose.Node -> Html msg
```

The port of `renderSelected` / `tagFor` (`Builder.elm:437-454`, `676-686`), made recursive:

```elm
renderNode node =
    Html.node (tagFor (Cem.Compose.componentOf node))
        (List.concatMap toAttribute (Cem.Compose.attrsOf node))
        (List.concatMap (renderSlot) (Cem.Compose.slotsOf node))


renderSlot : ( String, List Child ) -> List (Html msg)
renderSlot ( slotName, children ) =
    List.map
        (\child ->
            case child of
                Cem.Compose.ChildText t -> Html.span (placement slotName) [ Html.text t ]
                Cem.Compose.ChildIcon g -> iconElement slotName g
                Cem.Compose.ChildNode n -> withSlotAttr slotName (renderNode n)
        )
        children
```

`tagFor` and `toKebabCase` move here verbatim. Their correctness note is worth carrying across:
kebab-casing the fact's `component` noun is verified to match `M3e.Html`'s own tag literals for all
129 components, and is deliberately *not* re-derived from `@m3e/web`'s `custom-elements.json`,
which has at least one known-bad `tagName` (`StepperNextElement` lists `"m3e-stepper-previous"`).

`toAttribute : ( String, AttrValue ) -> List (Html.Attribute msg)` is the dispatch into the
consumer's kind table, mirroring `buildNonEnumAttr` / `setEnumAttr` (`Builder.elm:616-644`),
including the `Maybe.andThen` over `String.toFloat` / `String.toInt` so a half-typed number
contributes nothing.

The preview crosses into the typed world once, via `M3e.Unsafe.fromHtml`, exactly as
`Builder.elm:1365` does and for the same reason — which component is being rendered is only known
at runtime, so no typed constructor can produce it. This crossing will need an allow-list entry in
elm-m3e's `review/` config, the same way `App.Play.Builder` has one in `review-m3e`.

### 9.4 Fold 3 — codegen

```elm
codeFor : Cem.Compose.Node -> String
```

Generalises `codeSnippet` / `attrCodeLine` / `slotCodeLine` (`Builder.elm:770-856`) by recursing
into children rather than emitting a `{- default X instance -}` placeholder comment. Indentation
becomes a function of depth. Emits against one chosen facet (§8.6) — `M3e.Html.<component>
[ attrs ] [ children ]` for the `Html` facet, which is what `Builder.elm` emits.

Because `attrsOf` and `slotsOf` return sorted lists, `codeFor` is a pure function of the tree with
no ordering nondeterminism — snapshot-testable.

### 9.5 Adapter data and wiring

- **The kind table.** A `Dict String AttrKind`, built as in §5.3 from the consumer's own
  mechanically-derived `classify`. This is the bulk of the adapter work — `Builder/Attrs.elm` is
  1716 lines for M3e's 182 non-enum setters and 201 enum pairs. It is derivable by script, and the
  POC should derive it by script rather than by hand.
- **`tagFor`.** Six lines.
- **Value-setter dispatch.** `setEnumAttr` / `setBoolAttr` / `setStringAttr` / `setFloatAttr` /
  `setIntAttr`, ported from `Builder/Attrs.elm`.

### 9.6 Build wiring — required, and not currently satisfied

## 12. Alternatives considered

### 12.1 Batteries-included core with a default plain-HTML view — rejected

The alternative was a core that ships a working default view (plain `elm/html` cards, chips, and
menus) plus override points, so a new consumer gets something on screen immediately and replaces
widgets one at a time.

Rejected, for one decisive reason: **the actual first consumer would override essentially every
default.** elm-m3e's docs app renders through `TypedHtml`'s three-parameter phantom `Element` type
with `M3e.*` surfaces and `View.fromElement` at the boundary. A plain-`Html` default card is not a
partially-useful starting point for that app — it is unusable, because it does not typecheck into
the app's `Element` world at all without an escape hatch at every node. The defaults would serve
hypothetical future consumers rather than the one being built, at the cost of an `elm/html`
dependency in the core, an override-point API surface to design and maintain, and the permanent
temptation for library-specific behaviour to accumulate in the default view where it is invisible.

The headless split also buys the mechanical guarantee in §10: a package that cannot depend on
`elm/html` cannot leak a view. A batteries-included core would forfeit that.

The cost is real and accepted: the first consumer writes 100% of its view with no starting point,
and there is nothing to demo until a consumer exists. §13's testing strategy is the mitigation — the
core is fully testable with no view at all.

### 12.2 A generic `List Node`-only child model with a text sentinel — rejected

Covered at §5.5. Preserves the approved `children : Dict String (List Node)` at the cost of a magic
component name every fold must special-case. Rejected in favour of an explicit `Child` type.

### 12.3 Deriving attribute kinds inside the core — impossible, not rejected

Worth recording as *considered and found infeasible* rather than as a choice. A `Fact` contains no
type information for non-enum attributes; there is nothing in `Cem.Facts.Fact` from which
`"disabled" : Bool` could be inferred. The kind table must be injected (§5.3). The only alternative
would be extending `Fact` itself with an attribute-kind field in `elm-cem` — a much larger change,
touching the facts bundle schema, all four bundle consumers, and the M4 drift gate. If Compose
proves valuable, that is the right long-term fix and it would let the adapter shrink to `tagFor` plus
setter dispatch. Out of scope here. §14, risk 1.

### 12.4 Reusing `Builder.elm` in place — rejected

`Builder.elm` lives in `avetta/ui`, a private application repo, and imports `M3e` throughout. It
cannot be depended on. Compose extracts the *ideas* (and, for `slotInfos`, the literal logic) rather
than the module. `slotContentKind` is the one piece deliberately *not* carried across — see §8.7.

## 13. Testing strategy

`elm-test` over the core, in `packages/elm-cem-compose/tests/`. **The real 130-component facts are
not needed and should not be used** — a hand-written fake fact list of four or five components
exercises every branch, runs instantly, and does not break when `@m3e/web` bumps.

A sufficient fixture:

```elm
fakeFacts : List Fact
fakeFacts =
    [ blank "widget"
        |> withEnums [ ( "variant", [ "filled", "outlined" ] ) ]
        |> withAttrRewrites [ ( "disabled", "disabled" ), ( "label", "label" ) ]
    , blank "container"
        |> withMultiSlots [ "unnamed" ]
        |> withSlotKinds [ ( "unnamed", [ "widget", "ghost" ] ) ]   -- "ghost" is absent → omitted
    , blank "labelled"
        |> withRequiredSlots [ "headline" ]
        |> withSlotKinds [ ( "headline", [ "shared:text" ] ) ]
    , blank "iconic"
        |> withSlotKinds [ ( "lead", [ "shared:icon" ] ) ]
    , blank "single"
        |> withSlotKinds [ ( "only", [ "widget" ] ) ]               -- not multi → max = Just 1
    , blank "mixed"                                                 -- the §8.7 case
        |> withSlotKinds
            [ ( "any", [ "shared:text", "shared:icon", "widget", "ghost" ] )
            , ( "flowy", [ "shared:flow", "widget" ] )              -- flow is text, not a component
            , ( "unconstrained", [] )                               -- text only, never all-components
            ]
    ]
```

`blank : String -> Fact` fills the 14 `Fact` fields with empties; the `with*` helpers are record
updates. Total fixture: well under 60 lines.

Cases the suite must cover:

**Structure and addressing**
- `updateAt []` edits the root.
- `updateAt` at depth 3 edits the right node and leaves siblings byte-identical.
- `updateAt` on an out-of-range index / unknown slot / a `ChildText` target is a no-op returning an
  equal tree.

**Slot semantics** — the invariant most likely to regress
- `AddChild` twice on a `multiSlots` slot yields `filled = 2`, both children present, in order.
- `AddChild` twice on a non-multi slot yields `filled = 1` and the child is the **second**
  component, not the first (replace, not append, and not ignore).
- `AddTextChild` then `AddTextChild` on a non-multi slot replaces rather than duplicating.
- `RemoveChild` at index 0 of a two-element slot leaves the former index 1 at index 0.
- `RemoveChild` drops the whole subtree, not just the node.

**Query correctness**
- `attrChips` returns enum chips before plain chips, plain chips deduplicated and sorted.
- An `attrRewrites` name absent from `attrKinds` produces no chip (the `onClick` exclusion).
- A name in both `enums` and `attrRewrites` produces exactly one chip, the enum one.
- `isSet` is `False` before any `SetAttr` and `True` after — the specific divergence from
  `Builder.elm`'s always-emit-first-token behaviour, so it deserves a named test.
- `ClearAttr` returns `isSet` to `False`.
- `slotChips` reports `max = Nothing` for multi, `Just 1` otherwise.

**Slot affordances and menus** — the §8.7 decision; the behaviour most likely to be silently
regressed back to a precedence rule
- `mixed.any` yields `{ text = True, icon = True, components = [ "widget" ] }` — text and a
  component noun **coexist**. This is the named regression test for §8.7: an implementation that
  ported `slotContentKind` would report text-only here and this test is what catches it.
- `mixed.flowy` yields `text = True` (from `"shared:flow"`) *and* `components = [ "widget" ]` — the
  content-category tokens the old rule mishandled.
- `mixed.unconstrained` (empty `kinds`) yields `{ text = True, icon = False, components = [] }` —
  unconstrained never means "offer every component."
- `labelled.headline` (`[ "shared:text" ]`) yields text only; `iconic.lead` (`[ "shared:icon" ]`)
  icon only; `container.unnamed` components only. The three single-affordance shapes still work.
- `slotMenuOptions` on `mixed.any` returns exactly
  `[ OptionText, OptionIcon, OptionComponent "widget" ]` — order fixed, and `"ghost"` omitted
  because it is absent from facts.
- `slotMenuOptions` order is stable across repeated calls and independent of `kinds` order for the
  text/icon entries.
- **Every option `slotMenuOptions` returns produces a model change when its message is applied.**
  Property-shaped: for each fixture component and slot, map each option to its message, apply, and
  assert the tree changed. This is the mechanical form of §15's "no menu ever offers an option that
  produces no effect."
- `AddChild` with an unknown component name is a no-op — must agree with the menu omission.
- `AddTextChild` on a components-only slot (`container.unnamed`) is a no-op; `AddIconChild` on
  `labelled.headline` is a no-op. The converse of the line above: what the menu does *not* offer,
  the core does *not* do.

**Menu lifecycle**
- `OpenMenu` sets `openMenu`; `CloseMenu` clears it.
- Every structural message clears `openMenu`.
- `attrMenuOptions` on an unresolvable path returns `Nothing`.

**Determinism** — a property test, if `elm-explorations/test` fuzzing is worth the setup: applying
the same `Msg` list to two `init`s yields equal models, and `attrsOf`/`slotsOf` ordering is stable.
This is what makes the consumer's codegen snapshot-testable.

The consumer route is covered by the docs app's existing Playwright layer
(`docs/tests-browser/`) — a spec that loads `/components/compose`, clicks a chip, asserts a menu
opens, picks a value, and asserts both the live element and the snippet text updated. That is
integration coverage of the wiring, not of the logic; the logic is covered above.

## 14. Open questions and risks

**Risk 1 — the kind table is the adapter, and it is large.** `Builder/Attrs.elm` is 1716 lines. Any
second consumer pays a comparable cost, which weakens the "thin adapter" claim: the adapter is thin
in *concepts* (three things: kinds, tags, setters) but not in *lines*. Mitigations, in order of
preference: (a) derive it by script in the POC and ship the script, so the cost is a build step
rather than authorship; (b) longer term, extend `Cem.Facts.Fact` with attribute kinds in `elm-cem`
so it disappears (§12.3). **Open: should the POC ship the derivation script as part of
`elm-cem-compose`, or leave it consumer-side?** The script must import the library to verify setters
exist, which argues consumer-side — but then every consumer writes it again. Leaning consumer-side
for the POC and revisiting.

**Risk 2 — silent omission hides real facts bugs.** §6.5's silent drop means a `slotKinds` entry
naming a component that does not exist produces a quietly shorter menu. This is a deliberate,
recorded decision, and it matches `Builder.elm`'s existing posture, but note that D-031 is actively
changing the generated tree and a regenerated facts module with a renamed component would manifest
as *menus quietly losing options* rather than as an error. Cheap mitigation if it bites: a
`Cem.Compose.unknownSlotKinds : Model -> List ( String, String, String )` diagnostic query that the
consumer can render behind a debug flag. Not in the POC.

**Risk 3 — RESOLVED. The inherited `slotContentKind` precedence suppressed most nesting; it has been
replaced by non-exclusive `SlotAffordances`. See decision §8.7 and API §6.5.** The measurements
below are retained because they are the evidence for that decision and the baseline the POC's demo
targets are drawn from.

The superseded rule (`Builder.elm:505-524`) said: if `kinds` is empty, or contains `"html"`,
`"shared:text"`, or `"shared:link"`, the slot is text-only — *even when it also names nested
components*. Against the real facts that was not a corner case:

- **`button.unnamed`** lists 15 component nouns (`menuTrigger`, `dialogTrigger`, `heading`,
  `stepperNext`, …) alongside `shared:text`. Old result: text-only, **all 15 unreachable**. New
  result: text, icon, and all 15 offered.
- **`listItem.trailing`** lists `avatar`, `checkbox`, `radio`, `switch`, `heading` alongside
  `shared:text`. Old result: text-only — a user could not put a checkbox in a list item's trailing
  slot, one of the most ordinary things in the entire library. New result: seven options including
  the checkbox (Trace B, step 10).
- **`list.unnamed`** lists five component nouns and no `shared:*`. Nesting under both rules; it is
  unaffected, and it is the case Trace B step 4 uses.

**Measured across all 130 components** (script: classify every slot under each rule, build the
component→component edge set, find the longest simple path):

| Metric | Old rule | Decision §8.7 |
|---|---|---|
| Declared slots (union of `requiredSlots`, `multiSlots`, `slotKinds` keys) | 185 | 185 |
| Slots naming ≥1 resolvable component noun | 108 | 108 |
| …of those, **reachable** in the UI | 32 | **108** |
| …of those, **silently hidden** | **76** | **0** |
| Components with ≥1 nestable slot | **29 of 130** | **66 of 130** |
| Longest simple component-nesting chain | **3** | **5** |
| A maximal chain | `autocomplete > optgroup > option` | `appBar > searchBar > iconButton > bottomSheetAction > heading` |
| Self-recursive components → unbounded depth | `navMenuItem` | `heading`, `navMenuItem`, `treeItem` |

The old rule's numbers reproduce exactly, which is how the measurement script was validated. Note
that the old nesting set is a strict subset of the new one — **the decision takes nothing away**; it
only stops discarding.

Why it is 66 and not 130: the remaining 64 components name no component noun in any slot's `kinds`
at all. They are genuine leaves (`icon`, `divider`, `badge`, …), and no rule change makes them nest.
**66 of 130 is therefore the ceiling the facts allow, and the decision reaches it.** Anyone
expecting "nearly all 130" should read this row rather than assume.

Two data wrinkles the old rule mishandled, both fixed by §6.5's derivation: `kinds` also contains
`"shared:flow"` and `"shared:phrasing"` tokens that the inherited rule did not name at all, so they
fell through to its *component* branch — these are HTML content categories and are now classified as
text; and an empty `kinds`, documented in `Cem.Facts` as "unconstrained," is still text-only, now as
the deliberate narrow choice recorded in §6.5 rather than as a side effect of precedence.

**Residual risk, small.** Enumerating costs one extra click on any slot affording more than one
mode, and `button.unnamed`'s menu is 17 items. If a 17-item menu proves unwieldy, the fix is
consumer-side grouping (text/icon in one section, components in another) and needs no core change —
`SlotOption` is already partitioned by constructor. Accepted for the POC.

**Risk 4 — the elm-m3e package boundary is being re-decided in two places at once.** §11 and §11.1.
D-031 may rename the consumer's imports (`M3e.Component.Card` → `M3e.Card`); separately,
`origin/main` has 27 unabsorbed commits proposing a *different* 4-package layout, an
`elm-m3e-icons` package, and a `M3e.Forge.Internal` rename. Core unaffected in every scenario —
`Cem.Facts` and the `<Brand>.Review.Facts` contract survive all of them. Consumer rename is
mechanical but should not be paid twice. Mitigated by building the core first and deferring Phase B
until one boundary story wins.

**Risk 5 — the docs app cannot currently compile `M3e.Review.Facts`.** §9.6. `Cem.Facts` is not on
its source path. This is a two-line `elm.json` change but it is a hard blocker discovered during
this spec's research, not a known quantity, and it should be the *first* task of the consumer phase
so it fails fast if `../../elm-cem/facts/src` interacts badly with the vendored
`vendor/elm-foundation` tree.

**Risk 6 — chip re-click semantics in `m3e-filter-chip`.** §9.2. Believed not to apply, unverified.
Cheap to check in a browser; expensive to discover late.

**Risk 7 — scale of the chip-set.** Some components have many attributes. `m3e-button`'s
`attrRewrites` alone is substantial, and a card showing 20+ chips plus slot chips is a wall. The
POC accepts this. If it is bad, the fix is consumer-side (collapse unset chips behind a "+N more"
affordance) and needs no core change — `attrChips` already reports `isSet`, which is exactly the
partition key such an affordance would use.

**Risk 8 — no persistence means no shareable repro.** Non-goal 2. The main practical cost is that a
user cannot send a colleague a link to the tree they built. Mitigated by the copyable snippet, which
is the more useful artifact anyway.

## 15. Rollout and POC success criteria

Two phases. The first is decision-independent; the second waits on D-031 or accepts a rename.

**On decomposition.** This spec covers one coherent unit — a headless engine plus the one consumer
that proves it — but **Phase A and Phase B should be separate work units, not one**. They have
different dependencies (Phase B is blocked on the §11.1 boundary question, Phase A is blocked on
nothing), different verification (elm-test vs Playwright + a browser), and different failure modes.
Phase A is independently valuable: a tested, published headless package with no consumer is still a
real artifact, and it is the part that carries the portability claim. Do not start Phase B until
Phase A is green.

**The one decision that had to be made before Phase A has been made.** §14 risk 3's question —
whether a slot's content mode stays a winner-takes-all classification or becomes a set of
non-exclusive affordances — is resolved in favour of affordances (§8.7), and §5.5, §6.5, §7.2 and
§13 are written against that answer. Nothing in this spec is now blocked on a design decision;
Phase B remains blocked only on the §11.1 *boundary* question, which is a packaging matter, not a
Compose one.

### Phase A — the core

1. `packages/elm-cem-compose/` exists with the `elm.json` in §10.
2. `Cem.Compose` implements §5 and §6 in full.
3. `tests/` implements §13's suite against hand-written fake facts.
4. `pnpm run tasks` enumerates the new package; the workspace gate compiles it.

**Phase A is done when:** `elm-test` is green; the package compiles standalone; and `elm.json`
contains no `elm/html`, no `jackhp95/elm-m3e`, and no path outside the registry-faithful set.

### Phase B — the consumer

5. `docs/elm.json` gains the two `source-directories` entries (§9.6) and the docs app still builds.
6. `Route/Components/Compose.elm` implements the three folds (§9.2–§9.4).
7. Nav registration in `Shared.elm`; `check-nav.mjs` passes.
8. A Playwright spec in `docs/tests-browser/` covering one attr-set and one add-child.

**Phase B is done when all of the following are demonstrable in a browser:**

- Starting from an empty root, a user can build a tree **at least three levels deep** using only
  chips and menus — the specific thing `Builder.elm` cannot do. Under §8.7 this is no longer a
  narrow path: 66 of 130 components have a nestable slot and the longest simple chain is 5, so most
  reasonable starting points work. `menu > menuItemGroup > menuItem` remains a good scripted demo.
- **The §8.7 decision is visible in the browser, not just in the tests.** Two concrete checks, both
  impossible under the superseded rule:
  - `listItem`'s `trailing` slot chip opens a menu offering text, an icon, **and** `checkbox`, and
    picking `checkbox` puts a real `m3e-checkbox` in the rendered list item.
  - `button`'s default slot chip offers text alongside its 15 component nouns, and the user can
    choose either.
- **Unbounded depth is demonstrated, not just claimed:** `navMenuItem` accepts `navMenuItem` (as do
  `heading` and `treeItem` under §8.7), so nesting `navMenu > navMenuItem > navMenuItem > … ` to
  arbitrary depth must work with no cap, no guard, and no degradation. This is the acceptance test
  for decision §8.3.
- Every attribute chip that appears corresponds to a real setter, and setting it changes the live
  element's rendered appearance.
- The live preview and the snippet **agree** — pasting the snippet into a scratch module compiles
  and renders the same tree.
- No menu ever offers an option that produces no effect.
- The route compiles under elm-m3e's `review/` config, with at most the one documented
  `M3e.Unsafe.fromHtml` allow-list entry for the preview (§9.3).

### The portability criterion

The claim that Compose is generic is tested by dependency shape, not by writing a second adapter
(non-goal 3). It is satisfied when:

- `packages/elm-cem-compose/elm.json` depends on exactly `elm/core`, `elm-community/list-extra`, and
  `jackhp95/elm-cem-facts`;
- the core's entire test suite runs on fake facts, with no `M3e` anywhere in
  `packages/elm-cem-compose/`;
- and `grep -r "m3e" packages/elm-cem-compose/src` returns nothing, case-insensitively.

That last line is a one-line CI check and is the honest, mechanical form of the requirement.
