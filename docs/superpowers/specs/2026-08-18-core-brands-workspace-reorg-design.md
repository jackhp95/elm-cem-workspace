# core/ vs brands/ workspace reorg — design

Date: 2026-08-18
Status: draft, pending user review

## Problem

`packages/` currently holds library-agnostic codegen tooling (elm-cem, elm-cem-compose,
elm-review-cem, elm-html-intermediate-representation, elm-typed-html, cem-figma-connect)
jumbled together with library-specific derived output (elm-m3e, tailwind-m3e-web) and
hybrid packages that mix generic guidance with brand-specific implementation detail
(m3e-okf). There's no physical or naming signal for which packages are reusable across
any CEM-driven library ("brand") and which are tied to one.

The 2026-08-18 session-handoff plan doc's largest remaining item is proving the pipeline
is genuinely brand-pluggable by standing up a second real brand (e.g. Carbon) end-to-end,
gated in CI. That can't be convincingly proven while the directory layout doesn't even
distinguish agnostic from brand-specific.

## Scope of this pass

**Structure only.** M3E remains the sole brand after this reorg. Standing up a second
brand (Carbon) through the new layout is deferred to a follow-up phase, which will use
this reorg as its starting point and its acceptance test.

## Target layout

```
core/
  elm-cem/
  elm-cem-compose/
  elm-review-cem/
  elm-html-intermediate-representation/
  elm-typed-html/
  cem-figma-connect/
  tailwind-md3/                        (new — see "tailwind-m3e-web split" below)

brands/m3e/
  inputs/
    cem/                               (M3E's custom-elements.json + config/*.json)
    material-okf/                      (synced copy of the separate m3e-okf-adjacent
                                         Material-guidance repo — brand input)
  outputs/
    elm-m3e/                           (includes elm-m3e/docs/ as-is — no special treatment)
    tailwind-m3e-web/                  (slimmed — see below)
    m3e-api-okf/                       (enriched: material-okf's concepts +
                                         M3E-specific implementation guidance)
```

## Definitions

- **core/** = library-agnostic: works for *any* CEM + config, with zero knowledge of a
  specific brand. Determinism/codegen is not the qualifying test — genericity across
  brands is. (Material-anything does not qualify for core/, even though it's not
  generated by a pipeline — it's Material-specific, not brand-agnostic.)
- **brands/\<name>/** = everything specific to one library/design system, split into:
  - `inputs/` — what the pipeline (or a human) feeds in: the CEM + config, plus any
    brand-specific reference knowledge (e.g. material-okf) that isn't itself generated
    but is an input to what gets generated or enriched.
  - `outputs/` — what comes out: generated Elm packages, generated CSS, and any
    knowledge/guidance that's been enriched with brand-specific implementation detail
    (e.g. m3e-api-okf, which layers @m3e/web-specific guidance onto material-okf's
    generic concepts).

## m3e-okf split

Today's `m3e-okf` package mixes:
- `knowledge/{foundations,styles,components,expressive,patterns,anti-patterns,history}` —
  brand-neutral Material 3 guidance (consumed by the `applying-material-design` skill).
- `implementations/m3e-web/`, `skills/m3e/` — @m3e/web-specific API facts (exact
  `<m3e-*>` tags/attrs/slots), consumed by the `m3e` skill.

This already mirrors an existing skill-level distinction (`applying-material-design`
vs `m3e`), so the package split makes that boundary physical too:

- `knowledge/` → becomes `brands/m3e/inputs/material-okf/` — copied in from Jack's
  separate OKF repo as a brand input (not `core/`, since it's Material-specific, not
  brand-agnostic across arbitrary CEM libraries).
- `implementations/m3e-web/` + `skills/m3e/` → `git mv` to
  `brands/m3e/outputs/m3e-api-okf/`, with internal relative references fixed since
  `material-okf` is no longer a same-package sibling folder but a separately-synced
  input.

**Sync mechanism:** `material-okf` rides the existing snapshot/copy-fidelity
infrastructure already fixed this session for `m3e-okf` — add an entry to
`tools/snapshot-refs.json` (repo + pinned SHA) and a `copyFidelity` block in
`tools/family.json`, checked by the existing `copy-fidelity.mjs` gate wired into
`gate-all.mjs`. No new cron or separate automation; it piggybacks on gates that already
run.

## tailwind-m3e-web split

Current `packages/tailwind-m3e-web/src/` mixes two genuinely different things:

- `ref/palette.css`, `ref/_tone-table.css`, `theme.css`, `roles-extended.css` — pure
  Material-3-spec color science (OKLCH tonal-palette generation mapped to the official
  `--md-sys-color-*`/`--md-ref-palette-*` token names). Brand-neutral: any M3
  implementation uses this, not just @m3e/web.
- `sys/shape.css`, `sys/elevation.css`, `sys/density.css`, `sys/state.css`,
  `sys/typescale.css`, `sys/motion.css`, `sys/color.css` — deliberately, explicitly
  @m3e/web-specific: each file's header comments cite `node_modules/@m3e/web/dist/core.js`
  as source and state the values are chosen to match m3e's exact shipped internal
  defaults (e.g. elevation shadow layering mirrors m3e's `elevation(z)` helper
  byte-for-byte; typescale notes a deliberate divergence from an upstream m3e typo).
  This is a real, intentional compatibility bridge — not an accidental opinion — and
  stays brand-specific.

Split:
- `ref/` + `theme.css` + `roles-extended.css` → new package `core/tailwind-md3/` —
  generic M3 Tailwind theme, importable standalone by any M3-based brand.
- `sys/*.css` → stays in `brands/m3e/outputs/tailwind-m3e-web/`, which now depends on
  and re-exports `core/tailwind-md3` so existing consumers' import paths keep working
  through the brand package's barrel.

**Cleanup identified in the audit, not a design decision:** the private OKLCH
tone-calibration variables are named `--_m3e-tone-10-rich` etc. in `_tone-table.css`
and `ref/palette.css`, despite the calibration table having nothing to do with @m3e/web
— it's a generic OKLCH-to-HCT tone-matching lookup. Rename to `--_tone-*` (or
`--_md-tone-*`) as part of the move. These are private (leading-underscore) vars not
part of any public API, so the rename cannot break a consumer.

## Naming decisions (from the 2026-08-18 session-handoff doc's open questions)

- `tailwind-m3e-web` — name stays as the brand-output package name (it's now
  legitimately slimmed to just the @m3e/web bridge). No rename needed beyond the
  relocation.
- `cem-figma-connect` — stays as-is. Already generic in practice (m3-kit is just its
  first profile); the plan doc flagged this as low-urgency and nothing in this reorg
  changes that assessment.

## Non-goals of this pass

- Standing up a second brand (Carbon or otherwise) — deferred, becomes the acceptance
  test for this reorg in a follow-up phase.
- Any change to `elm-cem`'s CLI interface — it is already generic
  (`--flags-from=<CEM> --config-from=<config>... --output=<dir>`); this reorg only
  changes *where* brands point those flags, not the CLI itself.
- Publishing/mirror changes — untouched by this reorg; remains human-gated per the
  session-handoff doc's O-1 ruling.

## Open questions for implementation planning

- Exact CI/tooling references (paths in `package.json` workspaces globs, `gate-all.mjs`,
  `tools/family.json`, GitHub Actions workflows, any hardcoded `packages/<name>` paths)
  that need updating for every moved package — needs a full grep sweep during planning,
  not enumerated here.
- Whether `core/tailwind-md3` and `brands/m3e/outputs/tailwind-m3e-web` become separate
  npm/pnpm workspace packages with their own `package.json` (recommended, matches how
  `elm-typed-html` already depends on `elm-cem` as a sibling generic package) — to be
  confirmed during planning as a mechanical detail, not a design fork.
