Full spec is in `E-breadth-triage.md` cross-cutting #1. Summary:

**Approach A (inline `getEnum`) — DECIDED. Approach B rejected offline.**
- Published `.figma.ts` currently emits `const showIconGlyph = instance.getPropertyValue("Icon")`
  (`src/emit/html-label.mjs` `buildSlotBooleanBlock`, ~line 174-181) → a raw
  instance value, NOT a Material Symbols ligature → broken `name=`.
- FIX: thread the iconTable into the emitter and emit, per icon-bearing file:
  ```
  const glyph = instance.getEnum("Icon", {
    wifi: `name="wifi"`,
    stars_filled: `name="stars" filled`,   // symbolName + ` filled` when row.filled
    // …141 rows from the iconTable, keyed by figmaName
  })
  ```
  then `<m3e-icon slot="icon" ${glyph}></m3e-icon>` (parent OWNS the slotted tag).
- **Why not B (`getInstanceSwap` + nested icon CC):** proven unworkable OFFLINE.
  Code Connect nesting inserts the child's FULL render into a content position
  (`getInstanceSwap()?.executeTemplate().example`), no attribute injection / no
  attr-merge (`node_modules/@figma/code-connect/dist/html/parser.js` errors on
  duplicate attrs). A nested `<m3e-icon>` can't carry the parent's `slot="icon"`,
  and icons live in NAMED slots. A `<span slot="icon">` wrapper breaks
  `::slotted(m3e-icon)` + is non-idiomatic. And a shared-map import to dedupe the
  141 is impossible in CC 1.4.9 (`assertOnlyFigmaImports`: templates import ONLY
  `figma`). So the 141-enum inlines per icon-bearing file (generated/deterministic
  → byte bloat, not maintenance debt).
- Nesting DOES work for DEFAULT slots → the atoms-up composite plan is unaffected;
  B stays viable ONLY as a future standalone bare-icon CC layer.
